# D1 — Паритет F1-цикла, упакованного в скилл `pit-repair`, с прямым вызовом A2

Статус: `in_review`. Модель ремонта: `z-ai/glm-5.3-flash` через OpenRouter,
вызванная агентным харнессом OpenHarness 0.1.4, который сам подгружает
`SKILL.md`.

## Вопрос

Даёт ли починка через переиспользуемый скилл (агент сам решает вызвать
`pit-repair`, харнесс подгружает инструкцию, модель чинит и проверяет кодом
скилла) тот же результат, что прямой вызов из A2/A4, на тех же 76 программах
и той же модели?

## Метод и воспроизведение

**Скилл.** `.claude/skills/pit-repair/` (`SKILL.md`, `scripts/pit_check.py`,
`bin/pit-check`, `references/background.md`). Формат проверен
`skill-creator` (`quick_validate`: «Skill is valid»). `pit_check.py`
воспроизводит `pilot/a2_draft_validate.py`: та же AST-песочница, те же
`oracle.truncate` / `oracle.frames_equal` / `oracle.perturb_canary`, те же 15
сущностей `RandomState(0)`, таймаут 30 с, диагностические моменты
`2018-01-01, 2018-04-01, 2018-07-01` и held-out `2017-10-01, 2018-02-01,
2018-06-01`; чисто только при молчании обоих уровней на всех шести. Текст
починки в `SKILL.md` равен `F1_TEXT` из `pilot/a2_full_fetch.py` дословно.
Счётчик итераций ведёт сам скрипт (`pit_state.json`): итерация 0 =
детекция исходного кода, итерации 1..5 = кандидаты починки; ошибка
исполнения кандидата расходует итерацию, как в A2.

**Корпус.** Те же 76 программ из `pilot/a2_full_manifest.json`
(`source_code` по `program_uid`), без регенерации. Перед прогоном все 76
исходников прогнаны через `pit_check.py` без LLM: 74 дают `LEAK`, `uid`
совпал у 76/76; два исходника не исполняются в песочнице скилла
(`d81050e01947bda7`: `KeyError 'pay_type_debit_card'`; `c647c296f95c79e4`:
запрещённый `locals()`), тогда как загрузчик A1 (`_load_program`, без
песочницы) их исполнял. Для них итерация 0 = `ERROR`, цикл починки идёт
дальше как обычно. Контроли A2 на трёх диагностических моментах
воспроизведены тем же скриптом: корректная программа witness 0/3, canary
0/3; `naive_max` witness 2/3, canary 3/3; признак по дате доставки witness
0/3, canary 3/3.

**Харнесс.** OpenHarness 0.1.4 (`~/.openharness-venv/bin/oh`), режим
`-p … --output-format stream-json --max-turns 60 --permission-mode
full_auto`, рабочая директория = каталог программы с `get_features.py`.
Промпт агенту: `H.NEUTRAL_PROMPT` (постановка задачи и схема, как в A2) плюс
абзац «реализация лежит в `get_features.py`, проверь её на корректность по
времени (утечку данных из будущего) и почини в этом же файле; сообщи
вердикт». Имя скилла в промпте не упоминается; агент выбирает `pit-repair`
из списка скиллов в системном промпте (`skill(name=...)`).

Проверки из §3 плана, сделанные на месте:

1. *Формат и путь скиллов.* OpenHarness читает `<config>/skills/<name>/SKILL.md`
   и `skills/` плагинов; каталог `.claude/skills` проекта не сканирует.
   Frontmatter `name`/`description` совместим буквально. Скилл подключён
   симлинком `~/.openharness-d1/skills/pit-repair → .claude/skills/pit-repair`.
2. *Эндпоинт.* Профиль `provider=openai, base_url=https://openrouter.ai/api/v1`:
   тот же транспорт OpenRouter, что `litellm.completion("openrouter/…")` в A2.
   Отличие, которое нельзя убрать средствами OpenHarness 0.1.4: клиент не
   передаёт `temperature` и `reasoning.max_tokens` (A2: 0.2 и 1500),
   запросы уходят с дефолтами провайдера; `max_tokens` выставлен 14000, как
   в A2. Флаги `--settings` и `-k` в этой версии не действуют для профиля с
   `credential_slot`, поэтому ключ и профиль заданы через изолированный
   `OPENHARNESS_CONFIG_DIR` (`pilot/d1_make_ohcfg.py`), без переменных окружения.
3. *Батчевый режим.* `--output-format json` возвращает только финальный
   текст; `stream-json` отдаёт события `tool_started`/`tool_completed`/
   `assistant_complete`, по ним считаются ходы и проверяется факт вызова
   скилла. Ни ходов, ни стоимости OpenHarness в JSON не отдаёт; токены
   берутся из его сессионного снимка (`<config>/data/sessions/*/latest.json`),
   стоимость считается по прайсу OpenRouter и сверяется с дельтой
   `usage` ключа до и после прогона.

**Дисциплина безопасности.** Ключ лежит только в `settings.json`
изолированного конфига (mode 600); раннер удаляет `*_API_KEY` из окружения
процесса OpenHarness, так что Bash-инструмент агента и `pit_check.py` его не
видят; `pit_check.py` отказывается стартовать при наличии ключа в окружении
(агент в пробном прогоне сам проверил `env | grep …_API_KEY` перед запуском).

Команды:

```bash
uv venv ~/.venvs/pitbull-d1 --python 3.12 && uv pip install --python ~/.venvs/pitbull-d1/bin/python "pandas==2.2.3" "numpy==2.2.6"
python3 pilot/d1_make_ohcfg.py                       # ~/.openharness-d1 из .env
~/.venvs/pitbull-d1/bin/python pilot/d1_run.py       # pilot/d1_runs/<uid>/…
D1_PRICE_IN_PER_M=0.09 D1_PRICE_OUT_PER_M=0.30 python3 pilot/d1_score.py   # pilot/d1_results.json
```

Сырые артефакты: `pilot/d1_runs/<uid>/{pit_state.json,oh_stream.jsonl,run.json,get_features.py}`,
сводка `pilot/d1_results.json`, лог `pilot/d1_run.log`.

## Предрегистрированное правило решения

Скопировано из `skill-artifact-plan.md` §4 до прогона.

Основной вопрос: даёт ли починка через скилл тот же результат, что прямой
вызов из A2/A4, на тех же программах и той же модели?

Критерий «полного мэтча» (все три обязательны):

1. **Парное сравнение, не только агрегат.** Точный тест Мак-Немара на 76
   парных исходах (skill-run CLEAN/не-CLEAN на программу против A2
   CLEAN/не-CLEAN на ту же программу, по `program_uid`). `p > 0.05` — не
   найдено статистически значимого расхождения.
2. **Агрегат не хуже нижней границы A4.** CLEAN@5 (skill-run) ≥ 95.2%
   (нижняя граница 95% cluster bootstrap CI из A4).
3. **Нет нового класса отказа.** Любой провал скилла либо совпадает с уже
   известным (`deepseek-v4-flash-0731#79`, платёжный механизм), либо
   получает отдельное объяснение в отчёте.

Стоимость и число вызовов — не гейт, а диагностика: расхождение на порядок
(×10 по стоимости или по числу вызовов на программу) фиксируется как
практическое ограничение упаковки.

Если мэтча нет: до 5 раундов переработки `SKILL.md`, каждый с гипотезой,
повторным прогоном только по расходящимся программам и повторной проверкой
критерия; после 5 раундов без мэтча — `negative`/`neutral` с описанием
природы расхождения.

## Данные

Прогон 18–19 сентября 2026, 76 программ, все 76 сессий завершились штатно
(`run_status: ok`, ни одного таймаута и ни одной API-ошибки). Во всех 76
сессиях агент сам вызвал `skill(name="pit-repair")`; имя скилла в промпте
не упоминалось.

| Метрика | Скилл (D1) | Прямой вызов (A2) |
|---|---:|---:|
| CLEAN@1 | 75/76 = 98.7% | 65/76 = 85.5% |
| CLEAN@2 | 76/76 = 100% | 74/76 = 97.4% |
| CLEAN@3–5 | **76/76 = 100%** (Wilson 95% [95.2%, 100%]) | 75/76 = 98.7% |
| cluster bootstrap 95% CI для CLEAN@5 (100 000 выборок, seed 20260915) | [100%, 100%] | — |

По механизму (CLEAN@5, скилл / A2): `REVIEWS_NO_FILTER` 60/60 / 59/60;
`SELF_AVAILABILITY_CANARY` 14/14 / 14/14; `PAYMENTS_NO_FILTER` 1/1 / 1/1;
`VAR_MIXUP` 1/1 / 1/1.

**Парное сравнение.** Точный тест Мак-Немара: 0 программ чистых в A2 и нечистых у
скилла, 1 программа чистая у скилла и нечистая в A2; `p = 1.0`.
Единственная дискордантная пара:
`deepseek-v4-flash-0731#79` (`f1cade690ca333e8`), известный провал A2.
Разбор: в A2 модель на первой итерации добавила в код новый признак
`delivered_recency_days` по `order_delivered_customer_date`, и именно он
затем держался на canary четыре итерации подряд; исходная утечка
(`avg_review`, `total_reviews`, механизм отзывов) была починена. В D1
модель на первой итерации починила отзывы и ограничила `is_delivered`
условием `delivered <= seed_time`, нового признака не вводила; 27 → 26
столбцов. Исход остаётся в известном классе: A4 показал, что
на одной и той же review-программе один из трёх повторов может застрять на
canary, это вариативность генерации.

**Детекция на итерации 0.** 74/76 исходников дали `LEAK` тем же скриптом,
что в прогоне без LLM; 2 исходника (`d81050e01947bda7`,
`c647c296f95c79e4`) не исполнились в песочнице (`KeyError
'pay_type_debit_card'`, запрещённый `locals()`), получили `ERROR` на
итерации 0 и были очищены на итерации 1. Ложных `CLEAN` на итерации 0 нет.

**Учёт итераций.** В одном случае (`1c4cbd6256b111d8`) агент запустил
проверку дважды на неизменённом коде; повторный запуск засчитан как
итерация 1 (в state-файле отмечено `candidate identical to previous
iteration`), реальная починка легла на итерацию 2. Это единственная
программа с `clean_at = 2`; при учёте только изменённых кандидатов
CLEAN@1 = 76/76.

**Прокси «починки выбрасыванием»** (как в пилоте D; `pilot/d1_deletion_proxy.json`):
из 74 программ с расходившимися столбцами на итерации 0 в 68 все эти
столбцы сохранены в выходе после починки; в 3 форма выхода изменилась и
постолбцовое сравнение невозможно; в 3 часть столбцов удалена:
`684c03be8cf9af21` удалила все 20 расходившихся `delivery_days_*`
(235 → 205 столбцов, чистая «починка выбрасыванием»), `bf5c9bb63fa7cd53`
удалила 5 `avg_delivery_days*` и сохранила 10 review-столбцов,
`67fadf27cd93da36` удалила 1 из 8. Для A2 этот прокси не считался, поэтому
парного сравнения по нему нет.

**Стоимость и вызовы (диагностика, не гейт).**

| | Скилл (D1) | A2 |
|---|---:|---:|
| Вызовов модели | 578 (76 сессий × 7.6 хода в среднем; медиана 6, максимум 18) | 91 |
| Входных / выходных токенов | 7.98 M / 0.25 M | 0.31 M / 0.15 M |
| Стоимость по дельте `usage` ключа OpenRouter | **$0.478** | $0.1228 |
| Оценка по прайсу без учёта кэша (0.09 / 0.30 $ за 1M) | $0.79 | — |
| Время стены на программу | 159 с в среднем, максимум 662 с; весь прогон около 70 мин при 3 параллельных сессиях | — |

Расхождение ×3.9 по стоимости и ×6.4 по числу вызовов: не на порядок,
но заметно. Входные токены растут из-за системного промпта харнесса
(около 12 k токенов на ход) и повторной подачи истории на каждом ходе.
Разница между оценкой по прайсу и фактическим списанием объясняется
кэшированием префикса на стороне провайдера.

**Что делал агент сверх протокола.** В 10 сессиях из 76 агент перед
починкой прочитал исходники `prestudy/oracle.py` (списки
`SELF_AVAILABILITY_COLS`, `GATEKEEPER_COLS`, `TIME_COLS`), в 11 сессиях код
`pit_check.py`, в 12 сессиях исполнял собственные фрагменты python над базой,
чтобы посмотреть распределения дат. Все 10 «подсмотревших» сессии
длиннее обычных (10–18 ходов против 6–7) и все закончились `CLEAN`
(9 на итерации 1, одна на итерации 2, та же `1c4cbd6256b111d8`).
В A2 у модели такого канала не было: она видела только код и текст F1.
Это отличие условий прогона; протокол скилла соблюдён, на 66 остальных
сессиях агент шёл ровно по шагам SKILL.md. В одной сессии агент проверил
отсутствие ключей в окружении через `echo ${OPENROUTER_API_KEY:+SET}`,
ни в одной не редактировал `pit_state.json` и не обходил отказ скрипта.

Раундов переработки `SKILL.md` не потребовалось: критерий §4 выполнен с
первого прогона. Единственная правка скилла между пробным прогоном на
одной программе и основным: добавлен абзац о вердикте `ERROR`
(исправить причину и выполнить шаг починки в том же проходе).

## Вердикт

**positive**. Все три условия предрегистрированного критерия выполнены:
Мак-Немар `p = 1.0` (0 против 1 дискордантных), CLEAN@5 = 100% ≥ 95.2%,
единственное расхождение с A2 приходится на известный случай
`f1cade690ca333e8`, и оно в сторону скилла. Стоимость ×3.9 и число вызовов ×6.4 к A2 остаются
ниже порога «на порядок» и зафиксированы как практическое ограничение
упаковки.

## Вывод

Цикл «детекция witness/canary → F1 → проверка на held-out» переносится в
форму скилла без потери результата: агент на той же модели, выбирая скилл
сам, воспроизводит и превосходит CLEAN@k прямого вызова (75/76 уже на
первой итерации против 65/76 в A2). Часть прироста на k=1 объясняется тем,
что агент в скилле видит вывод детектора с именами столбцов и может читать
исходники оракула, тогда как в A2 модель получала только текст F1; для
статьи это формулируется как «не хуже»; заявлять превосходство нельзя. Для Artifact
Evaluation `pit-repair` становится отдельной строкой в составе артефакта.

Ограничения: одна модель и одна база; OpenHarness 0.1.4 не даёт
выставить `temperature` и бюджет рассуждений (в A2: 0.2 и 1500), так что
сравнение идёт при дефолтах провайдера; каталог скиллов у OpenHarness
свой (`<config>/skills/`), для других харнессов совместимость пути надо
проверять отдельно; в скилле песочница строже загрузчика A1 (два
исходника не исполнились на итерации 0); один прогон на программу, без
повторов. Черновик формулировки для статьи и блок для `docs/PLAN.md`
приведены в `skill-artifact-plan.md` §6–7 и предложены отдельно, без
самостоятельного применения.
