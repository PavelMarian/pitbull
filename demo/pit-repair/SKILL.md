# pit-repair: детекция и починка утечки из будущего

Скилл упаковывает цикл, провалидированный в экспериментах A2/A4 проекта
PITBULL: дифференциальное исполнение находит утечку, модель чинит код по
фиксированной формулировке обратной связи, исполнение подтверждает починку
на held-out моментах. Ничего из этого не заменяется чтением кода «на глаз»:
пилот показал, что модель без исполняемой проверки находит утечку в 1 из 12
программ, а с названным классом ошибки чинит 11 из 12.

## Интерфейс проверяемой функции

```python
def get_features(db: dict, entity_ids, seed_time) -> pd.DataFrame
```

`db`: словарь таблиц pandas (для Olist: `orders`, `order_items`,
`reviews`, `payments`); `entity_ids`: список сущностей; `seed_time`:
`pandas.Timestamp`. Результат индексирован по `entity_ids`. Доступны только
`pd` и `np`. Если реальный код устроен иначе, его оборачивают в такую
функцию; обёртке разрешена перестановка вызовов, запрещена логика признаков.

## Шаги

### 0. Предусловия

- Python с pandas 2.2.x и numpy 2.2.x (в проекте закреплены 2.2.3 / 2.2.6).
- Данные Olist: переменная `P3_OLIST` или `<корень PITBULL>/PITFALL_olist_data`.
- Команда проверки: `pit-check` (обёртка `bin/pit-check` этого скилла; если
  её нет на PATH, вызывайте `python <каталог скилла>/scripts/pit_check.py`).
- В окружении процесса проверки не должно быть ключей LLM-провайдера
  (`OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`). Скрипт
  исполняет сгенерированный код и при наличии ключа отказывается работать.
  Не экспортируйте ключи и не обходите отказ: сетевой этап и этап
  исполнения должны быть разными процессами.

### 1. Детекция

```bash
pit-check --code get_features.py
```

Скрипт вызывает функцию трижды на каждом моменте: на полной базе, на базе,
усечённой по `seed_time` (`oracle.truncate`), и на базе с типовым
canary-возмущением поздно доступных полей (`oracle.perturb_canary`).
Моменты по умолчанию: диагностические `2018-01-01, 2018-04-01, 2018-07-01`
и held-out `2017-10-01, 2018-02-01, 2018-06-01`; вызывающий может передать
свои через `--dev-seeds` / `--held-out-seeds`.

Две строки в выводе:

- `witness`: столбцы, которые разошлись между полной и усечённой базой.
  Это доказательство: функция прочитала строки с временем позже `seed_time`.
- `canary`: столбцы, которые разошлись между полной и возмущённой базой.
  Функция прочитала поля, которые заполняются позже покупки (дата доставки,
  отзыв, ответ на отзыв, статус заказа).

Вердикт `CLEAN` только если оба уровня молчат на всех шести моментах.
Вердикт `CLEAN` на итерации 0 означает, что чинить нечего: сообщите это и
остановитесь. Вердикт `ERROR` означает, что кандидат не исполнился в
песочнице (ошибка времени выполнения или запрещённая конструкция, например
`locals()`, файловый или сетевой вызов): устраните причину и в том же
проходе выполните шаг починки, потому что утечка при этом никуда не делась.

### 2. Починка

При вердикте `LEAK` перечитайте текущий код и выполните следующую
инструкцию дословно, как если бы её адресовали вам вместе с кодом выше:

```
В коде выше может быть утечка данных из будущего. Требование: признаки
для момента seed_time должны вычисляться ТОЛЬКО по информации, которая уже существует
на момент seed_time. Учитывай, что события в базе появляются в разное время: например,
отзыв на заказ пишется позже самой покупки, а даты доставки заполняются после неё.
Проверь свой код на это требование и верни исправленную версию функции get_features
(та же сигнатура), в одном блоке ```python ...```, без пояснений.
```

Запишите исправленную функцию целиком в тот же файл (`get_features.py`),
заменив прежнюю версию. Сигнатура и имя функции остаются прежними, импорты
только `pandas`/`numpy`. Текст инструкции выше зафиксирован в экспериментах
A2/A4 (промпт F1); не пересказывайте его и не дополняйте своими
подсказками о конкретных столбцах: сравнимость с этими экспериментами
держится на неизменности формулировки.

### 3. Повторная проверка

Запустите ту же команду:

```bash
pit-check --code get_features.py
```

Скрипт сам ведёт счёт итераций в `pit_state.json` рядом с кодом и каждый
раз проверяет все шесть моментов, включая held-out, которые модель не
видела в вердикте детекции. Ошибка исполнения кандидата тоже расходует
итерацию: так считалось в A2.

### 4. Цикл и остановка

Повторяйте шаги 2 и 3, пока не получите `CLEAN`, но не больше пяти
итераций починки. После пятой неудачи скрипт ставит статус `failed` и
печатает `FAILED`; дальше не чините, а отчитайтесь. Не редактируйте
`pit_state.json` руками и не удаляйте его, чтобы «обнулить» счётчик.

## Итоговый отчёт

Завершайте работу коротким отчётом такого вида (значения берите из
последнего JSON-вывода `pit-check` и из `pit_state.json`):

```
pit-repair: verdict=<CLEAN|FAILED>, clean_at=<итерация или null>,
iterations_used=<n>, witness_final=[...], canary_final=[...],
state=<путь к pit_state.json>
```

## Как читать спорные случаи

- Witness даёт доказательство, canary даёт сильный сигнал. На заведомо чистых
  программах canary даёт ложное срабатывание в 4 из 30 случаев (13.3%, A5).
  Одно срабатывание canary на программе, у которой witness молчит,
  формально считается «не CLEAN» по протоколу, но стоит назвать столбец и
  механизм в отчёте, чтобы человек мог отличить ложное срабатывание от
  реальной утечки.
- Три канала, на которых чтение кода моделью расходится с картой чекера
  (A3): изменяемый `order_status`, задержанная доступность платежа,
  `review_answer_timestamp` вместо принятого картой `review_creation_date`.
  Если проверка ловит именно их, чините под карту чекера: она является
  референсом протокола, и спор с ней в отчёте уместен, а в коде нет.
- Известный провал прямого вызова: `delivered_recency_days` на программе
  `f1cade690ca333e8` (A2) держится на canary после пяти итераций. Такой же
  исход здесь ожидаем и не является дефектом скилла.
