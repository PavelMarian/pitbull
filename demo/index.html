Pavel Marian, Stanislav Chumakov, Danil Ezhov, Alexander Boukhanovsky · AI Institute, ITMO University, Saint Petersburg

TL;DR

Relational feature programs often join records whose values become available at different times. PITBULL turns point-in-time correctness into an executable check, names the table and column whose late-arriving values caused the difference, repairs the program, and verifies the candidate on unseen prediction times. The whole loop is packaged as a skill that a coding agent can load and run on its own.

Experiments

        

      

      
Data: the Olist e-commerce database (Brazil, 2016–2018), four tables, one task: will a product be ordered in the 90 days after seed_time? Two code models wrote feature programs from a plain task description; the checker found 76 that read the future.

            Why is the last one so stubborn?
            
The agent fixed the review leak on the first try, but while rewriting it added a new feature: days since the product's last delivery, read from order_delivered_customer_date.

            
The order was placed before seed_time, so the past-only run keeps it and the witness is silent. The delivery date is filled in later, when the parcel arrives. The canary rewrites such late fields, and the feature moves on all six prediction times.

            
The agent kept the feature for four more iterations; it treated an old order as fully known.

            
The checker still rejects this program. A canary hit blocks acceptance, so the code never counts as clean.

          Experiment 2
          
Does the result survive another generation?

          
Experiment 2 repeats repair generation three times. The question is whether success depends on one lucky model response or remains stable across independent runs.

          
Pick a repetition, or all three together.

        

        

          

            
            
            
            
          

          
Repeat 1 leaves one program unresolved and reaches 61 clean programs.

          

            Why does one program fail in two of three runs?
            
It is the only program that leaks through payments. It creates one output column per payment type found in the payments table.

            
The agent filters the payment rows by seed_time but still reads the list of types from the full table. On the past-only database a type that appears only later is missing, so the set of columns changes. The checker reports a shape difference on every prediction time.

            
The leak is in the output schema, not in the values. The repair instruction talks about values, so the agent fixed it only in repeat 1, by chance, at iteration 2.

          

        

      


      

        

          Experiment 3
          
How much temporal coverage is enough to expose a leak?

          
Experiment 3 varies the number of prediction times at which a program is checked, from one to five.

          
Witness: the program is run with and without the rows dated after seed_time. A different output proves it read the future.

          
Canary: in rows dated before seed_time, fields that get filled in later (delivery date, review) are replaced by marker values. A changed output shows the program read a field that was not yet known.

Key findings

      

      
    
        
  1. Experiment 1
    75 of 76 leaking programs were repaired within five iterations, 65 of them at the first one. The last program keeps reading a delivery date that is filled in later; the canary catches it every time, and the checker never accepts it.
    2. 
        
  2. Experiment 2
    182 of 186 program–run pairs came out clean across three independent repair runs. The result does not depend on one lucky generation.
    3. 
        
  3. Experiment 3
    The witness gave 0 false positives on 30 clean programs. Two prediction times expose 97.6% of leaks, five expose 99.4%.
    4. 
        
  4. Skill
    Packaged as a skill, the same loop repaired 76 of 76 when an independent coding agent chose it on its own; paired comparison with direct invocation shows no difference.
    5. 
      

    


    

      

        
Limitations

      

      
One database and one task (Olist, will a product be ordered in the next 90 days), two author models and one repair model; 60 of the 76 leaks go through reviews, the other mechanisms have one to fourteen programs each. The availability map is written by hand, per table, and the check is only as good as it. CLEAN means no difference on the six tested prediction times under that map, which is evidence and not a proof. The canary flagged 4 of 30 clean programs and blocks acceptance, so canary-only cases need a person to look. The skill run is one pass per program, and inside the agent harness the model could read the checker's source, which direct invocation could not.

    


    

      

        
Reusable skill

        
The same loop, packaged for coding agents. The agent loads the skill, runs the check on a feature program, rewrites it when a leak is found, and repeats until the code is clean on development and held-out prediction times, at most five times. A canary hit blocks acceptance. On the same 76 programs an agent that chose the skill on its own repaired 76 of 76.
